# tpmk_analyzer

BI-аналитическое приложение для загрузки Excel-файлов, обработки ассортимента, сохранения данных в PostgreSQL и формирования отчетов в XLSX.
Количественные показатели BI:
- Размерность ежедневных данных 50 колонок х 30 000 строк
- Периодичность: день - месяц - год
- Общий период хранения данных - 5 лет
- **ИТОГО:** ~ 11 000 000 строк в год

## Цель проекта

### Стратегическая
Корпоративное приложение:
- для учета пользователей, ассортименита (OLTP)
- BI-ресурс для ежедневного анализа коммерческих показателей: закуп, продажи, справочная информация (OLAP)

### Оперативная
Сделать систему, которая:
- принимает Excel-файл с данными;
- анализирует ассортимент;
- выделяет два датафрейма для сохранения в два XLSX-файла;
- сохраняет данные в PostgreSQL;
- показывает результаты в web-интерфейсе;
- в перспективе развивается в полноценный BI-ресурс с графиками, таблицами и фильтрами.

## Выбранный подход

### MVP UI
Для быстрого старта используется Python-based web UI:
- Streamlit — если нужен максимально быстрый прототип;
- Dash — если нужен более контролируемый и “BI-шный” интерфейс.

### Backend
- FastAPI как ядро API.
- Отдельные сервисы для чтения, валидации и трансформации Excel.
- Отдельные воркеры для тяжелой обработки и генерации файлов.

### Хранилище
- PostgreSQL для исходных, очищенных и аналитических данных.
Разные БД для OLTP и OLAP, партицинирование по месяцам.
- XLSX-файлы как артефакты обработки.

## Архитектура

```text
UI (Streamlit / Dash)
        ↓
FastAPI
        ↓
Service layer
├── Excel handlers
├── Data transformers
├── Report generators
        ↓
Worker layer
        ↓
PostgreSQL
        ↓
XLSX storage
```

## Основные слои

### 1. UI слой
Отвечает за:
- загрузку Excel;
- отображение статуса задач;
- фильтры и графики;
- просмотр таблиц;
- скачивание XLSX-результатов.

### 2. API слой
Отвечает за:
- прием файлов;
- создание задач обработки;
- получение статусов;
- выдачу результатов;
- работу с данными для UI.

### 3. Service layer
Отвечает за:
- чтение Excel;
- нормализацию данных;
- бизнес-валидацию;
- формирование итоговых датафреймов;
- подготовку данных для отчетов.

### 4. Worker layer
Отвечает за:
- выполнение тяжелых операций;
- запись данных в PostgreSQL;
- генерацию XLSX;
- подготовку данных для графиков и BI-отчетов.

### 5. Data layer
Отвечает за:
- raw-данные;
- staging-данные;
- analytics-данные;
- историю обработок;
- метаданные файлов и задач.

## Поток обработки

```text
1. Пользователь загружает Excel.
2. UI отправляет файл в FastAPI.
3. FastAPI создает job.
4. Worker читает Excel и обрабатывает данные.
5. Данные сохраняются в PostgreSQL.
6. Формируются два XLSX-файла.
7. UI показывает статус и результат.
8. Пользователь скачивает итоговые файлы или смотрит аналитику.
```

## Почему так

- FastAPI хорошо подходит для API-ядра и фоновой обработки
- Streamlit и Dash позволяют быстро собрать MVP без отдельной фронтенд-команды
- Для FastAPI-проектов хороша явная декомпозиция на routers, services, models, schemas и tests.

## MVP-границы

На первом этапе не делаем:
- сложную авторизацию;
- микросервисы;
- полную BI-метрическую платформу;
- сложный frontend на React.

На первом этапе делаем:
- upload Excel;
- обработку;
- запись в PostgreSQL;
- генерацию двух XLSX;
- простую панель с таблицами и графиками.

## Дальнейшее развитие

После MVP можно добавить:
- роли пользователей;
- историю запусков;
- dashboard с KPI;
- semantic layer для метрик;
- полноценный frontend на React/Next.js;
- экспорт в дополнительные форматы.
